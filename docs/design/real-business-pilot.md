# 真实业务试点执行方案

## 目标

用一个真实的前端或全栈小需求验证 Factory 是否能完成：

```text
需求 → task_id → requirement → spec → AI 编码 → 质量门禁
→ 独立审查 → Mock/API 验证 → 浏览器验收 → 受控交付
```

试点优先选择有页面状态、接口文档、权限逻辑和可复现测试环境的需求。不要选择纯文档任务、没有验收环境的任务或需要一次性大范围重构的任务。

## 任务产物

每个试点任务必须产生并绑定：

- `task_id` 和任务身份文件
- `requirement.md`
- `spec.md`
- 代码变更和提交 SHA
- 阶段收据与日志
- 设计证据或接口契约/Mock 证据
- 本地质量门禁结果
- 独立审查结果
- 测试环境浏览器/API 验收结果
- MR/CI/部署状态（若任务包含远端交付）

## 状态语义

| 状态 | 含义 | 是否允许推进 |
| --- | --- | --- |
| `PASSED` | 检查已执行且通过 | 是 |
| `FAILED` | 检查已执行但失败 | 否 |
| `NOT_RUN` | 检查尚未执行 | 否 |
| `BLOCKED` | 因证据、权限或环境问题无法执行 | 否 |

## 退出标准

试点必须由同一个 task_id 串起需求、spec、代码、验证和交付证据。任何版本漂移、证据缺失、未执行检查、失败后继续推进或远端状态不可回读，均阻断任务完成。

## 数据采集

从第一批试点开始记录：需求到 spec 耗时、编码耗时、首次验收通过率、失败分类、恢复耗时、重试次数和模型成本。数据先写入任务收据，后续再汇总为团队指标。
