# ADR-017 · 2026-09-19 · 双层反馈范式自述（执行层 OODA × 治理层 PDCA）

**背景**：会话门禁与全局规则持续累积但无统一范式自述，规则演进缺坐标
系。判定依据：全仓 grep `PDCA|OODA` 零命中（无先占声明）；现有机制可
二分层归位——执行层规则规范「面对不确定性如何快速修正判断」，治理层
规则规范「如何把教训沉淀为确定性约束」。

**决策**：
1. **执行层 OODA**：目标模糊先 grill（Orient 前置）；API 盲试错门禁
   （同一端点 2 次失败禁发第 3 次，转权威文档/子代理）压缩 Observe→
   Orient 成本上限；异构对抗/反向角色校正 Orient 偏差；获得明确授权后 commit 即 push、
   长会话收尾门禁压回路周期（tempo）。
2. **治理层 PDCA**：否决沉淀（人类否决 → 门禁/checklist/ADR =
   Act→标准化）；doc-freshness、mutation/负控制测试 = Check 机械化
   （靠 CI 不靠纪律）；holdout 只用于验收不回流调参 = 防 Check 污染 Plan。
3. **层间接口**：OODA 循环中的教训须过「归因断言须时间窗证据定案」
   （在场 ≠ 因果，见 dispatch_watch 更正）才准入 PDCA 沉淀；两层不
   混用——执行层禁以「计划已定」跳过观察（`--help` 非安全探针），
   治理层禁以「快速迭代」绕过接线（人工同步只做存量清理，不新增靠
   人工纪律的约定）。
4. **命名纪律**：对外描述本项目用机制三件套（确定性门禁注入 + 负控制
   验证 + 否决沉淀），不借 PDCA/OODA 标签——避免读者带入 PDCA 的
   计划驱动框架偏差。

**验证**：范式自述型 ADR，无可执行测试。falsifier：后续新规则若无法
归入任一层、或需违反层间接口约束才可落地，须修订本 ADR 而非静默绕过。
