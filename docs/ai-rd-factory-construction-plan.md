# AI 研发工厂建设规划

## 目标

将业务需求稳定地交给本地 Factory 完成：

```text
需求分类 → 技能发现 → 设计/接口证据分析 → requirement → clarification → spec → 独立 spec-review
→ AI 编写代码 → 本地验证 → 质量门禁 → 分支提交 → 远端交付
```

Factory 负责编排和状态推进，规则仓负责规范与门禁，浏览器/Figma Connector 负责真实页面证据。
任何一层不能用模型自述替代另一层的证据。

## 当前基线

| 能力 | 归属 | 状态 |
| --- | --- | --- |
| 前端/后端/全栈/本地模式初始化 | awesome-factory | 已实现，本轮补回归 |
| 本地阶段状态、恢复、租约和失败收据 | 业务仓 `.factory` | 已实现 |
| Figma 设计契约和视觉验收 | awesome-rules | 已实现 |
| 验收契约、红绿事故回归 | awesome-factory + awesome-rules | 已实现 |
| 云效/GitHub 推送、MR、流水线 | Factory/DevOps 适配层 | 受远端权限和平台配置约束 |

## 阶段计划

本规划采用“平台能力与真实业务交付同步验证”的原则。Factory 的能力只有在真实业务需求中完成从 spec 到联调验收，才算有效；单独的脚本通过或本地模型输出不能替代业务闭环证据。

### P0：初始化与本地闭环

- `factory-init` 自动识别 frontend/backend/fullstack。
- `--mode local` 只安装本地链路需要的文件。
- 生成 `factory-local.json`，明确 `remote_side_effects=false` 和 `auto_commit=false`。
- 本地 runner 固定阶段：`classify → skill-discovery → design-analysis → requirement → clarification → spec → spec-review → preflight → implement → review → verify`。
- 每个阶段保存状态、收据、日志、退出码和恢复命令。

完成标准：初始化 profile 回归测试通过；业务仓可以从 request 文件恢复到任一阶段；本地任务自动生成稳定 `task_id`，并绑定状态、阶段收据、日志和证据。

### P0：真实业务试点

在平台继续扩展前，选定一个真实的前端或全栈小需求作为样板，完整执行：

```text
需求确认 → task_id → requirement → clarification → spec → 独立 spec-review → AI 编码
→ 增量质量门禁 → 独立审查 → Mock/API 验证 → 浏览器验收
```

试点不得选择纯文档或无可复现环境的需求。优先选择有页面状态、接口契约、权限逻辑和测试环境的中小型需求。

退出标准：同一个需求在一个任务目录中完成 spec、代码、测试环境验收和交付证据；失败可以从收据记录的阶段恢复；未执行的检查明确标记为 `NOT_RUN`，不能标记为通过。

### P1：证据驱动的需求和设计链路

- 有 Figma 时先做 Connector 登录预检。
- 采集 `design-evidence.json` 和节点截图。
- 生成 `design-contract.json`，再生成确定性的 `visual-contract.json`。
- P0 布局必须绑定 DOM 测量、Figma 截图和页面截图。
- 没有真实设计证据时阻断，不得声称 UI 已还原。

完成标准：视觉契约、节点映射、尺寸测量和浏览器收据全部通过。

### P1：接口文档和 Mock 链路

- 先读取接口文档并冻结 method/path/请求/响应字段。
- 生成与契约一致的 Mock 数据。
- Mock 只用于本地开发和页面验证，不能替代真实接口验收。
- 接口契约变更同步实现、Mock、测试和 spec。

完成标准：接口契约检查通过，空态/错误态/加载态均有证据。

### P1：统一验收契约与增量门禁

- 统一记录 `PASSED`、`FAILED`、`NOT_RUN`、`BLOCKED`，禁止把未执行当作通过。
- 验收契约绑定 `task_id`、需求版本、spec 摘要、代码提交 SHA、规则版本、测试命令、测试环境和证据索引。
- 新增或修改范围必须通过增量质量门禁；存量问题单独建立可信基线。
- 构建、安全检查和关键集成检查仍保留全量底线，不因历史问题而跳过。
- 规则审查和规格审查分离执行，阻断问题修复后必须重新审查。

完成标准：试点任务能够生成一份完整 evidence manifest；任何证据缺失、版本漂移、检查未执行或证据过期都会阻断交付。

### P1：前后端契约与联调

- 前后端任务拆分为带依赖关系的 DAG。
- 接口 method/path/请求/响应字段先冻结，再分别生成实现、Mock 和测试。
- 联调失败必须记录责任边界、失败分类和恢复节点。
- 集成测试必须绑定同一 task_id、契约版本和代码版本。

完成标准：前端、后端和集成验证可以独立回读；契约变更会阻断旧 Mock 或旧测试继续背书。

### P1：质量门禁与交付

- 开发分支提交前运行规则门禁、单测、类型检查、构建和必要的视觉门。
- 质量门禁失败不得进入远端开发分支。
- 提交、推送、MR、流水线状态分别记录，不混写为“已完成”。
- 分支保护由远端平台执行，Factory 不绕过保护规则。

完成标准：本地门禁通过，远端 ancestry 可回读，MR/流水线状态可核验。

### P2：事故闭环和持续改进

- 用户缺陷保留精确事故身份、基线、修复提交和红绿测试收据。
- 失败按 missing-context、wrong-approach、environment-issue、external-blocker 等分类。
- 同一失败签名最多重试三次，重试必须改变策略或增加证据。
- 可泛化经验必须有独立评测后才进入规则仓。

### P2：团队协作和指标

- 每个任务必须有负责人、分支、task_id 和当前恢复责任人。
- 记录需求到验收的耗时、首次验收通过率、失败分类、恢复耗时和模型成本。
- 先用任务收据和日报采集数据，不等待独立指标平台完成。
- 自动提交、MR、合并和发布仍由远端权限与人工授权控制。

## 统一完成判定

任务只有在以下证据齐全时才能标记完成：

1. requirement 和 spec 已保存并与请求绑定；
2. 代码改动在任务分支完成；
3. 本地验证和质量门禁有退出码；
4. Figma/API/Mock 证据按任务类型完成；
5. 失败和重试有记录；
6. commit、远端分支、MR 或权限阻断状态可回读。

## 调整后的实施顺序

1. 已完成：为初始化 profile 增加回归测试和文档基线。
2. 已完成：业务仓本地 runner 调用视觉守卫时强制传递 `design-contract.json`。
3. 已完成：定义七阶段收据、manifest 和统一 fail-closed 验收器。
4. 当前最高优先级：选择一个真实业务需求，跑通单项目端到端试点，并补齐 `PASSED/FAILED/NOT_RUN/BLOCKED` 状态。
5. 下一步：把统一验收契约接入业务仓 runner 的所有阶段，绑定 task_id、代码版本、规则版本和证据索引。
6. 再下一步：接入增量门禁、双轴审查、前后端契约 DAG 和测试环境验收。
7. 最后：接入云效分支/MR/流水线状态回读，再推广到第二个业务项目和团队协作指标。

## 真实业务试点退出清单

试点只有同时满足以下条件才算完成：

1. request、requirement 和 spec 已保存并绑定同一 `task_id`。
2. 代码改动位于任务分支，提交 SHA 可回读。
3. 增量质量门禁和必要的全量底线检查有退出码。
4. 前端任务有设计证据；接口任务有契约和 Mock 证据；需要浏览器验收时有真实页面收据。
5. 独立规范审查和规格审查均完成，阻断项已复验。
6. 测试环境验收明确区分通过、失败、未执行和阻断。
7. 失败、恢复和重试均有记录，旧证据不会为新代码背书。
8. MR、CI、部署和发布状态分别记录；未执行的远端动作不能描述为完成。

公共能力分层与现行接入以 [shared-local-workflow](design/shared-local-workflow.md) 为准；三项控制已从业务仓移入公共运行时，项目只配置和适配。云效平台侧多仓 checkout 与真实环境验收须单独验证。
